# Специфікація вимог до програмного забезпечення (SRS)

*Документ сформовано відповідно до структури міжнародного стандарту ISO/IEC/IEEE 29148.*

## 1. System Context

Межі системи (Scope) охоплюють: реєстрацію та автентифікацію користувача, управління цифровим гардеробом, асинхронний аналіз зображень одягу засобами комп'ютерного зору, формування персоналізованих рекомендацій образів та аналітику використання речей. Поза межами системи: онлайн-оплата, маркетплейс купівлі одягу, соціальна мережа між користувачами.

Актор: Користувач (Person) — власник гардероба, взаємодіє із системою через Web SPA (REST/HTTPS).

Зовнішні системи (System_Ext): Email Provider (SMTP) — використовується для надсилання транзакційних листів підтвердження реєстрації. Усі ML-обчислення виконуються власним інференс-сервісом системи; сторонні ML-API в межах MVP не використовуються.

## 2. Functional Requirements

| ID | Вимога |
|---|---|
| SRS-FUN-01 | Система повинна реалізовувати реєстрацію та автентифікацію користувача за протоколом OAuth 2.0/OIDC з видачею підписаного JWT-токена (алгоритм RS256). |
| SRS-FUN-02a | Система повинна приймати завантажене користувачем зображення речі та зберігати його в об'єктному сховищі (Object Storage). |
| SRS-FUN-02b | Система повинна ставити завдання асинхронного CV-аналізу збереженого зображення в чергу повідомлень RabbitMQ. |
| SRS-FUN-03 | Система повинна виконувати автоматичну класифікацію типу, кольору та сезонності речі засобами ML-інференс-сервісу на основі CLIP-подібної моделі. |
| SRS-FUN-04 | Система повинна зберігати векторне представлення (embedding) кожної класифікованої речі в базі даних PostgreSQL. |
| SRS-FUN-05 | Система повинна формувати рекомендації комбінацій одягу методом content-based filtering на основі косинусної схожості embeddings з урахуванням сезону та стилю. |
| SRS-FUN-06 | Система повинна приймати фідбек користувача (лайк/дизлайк) щодо рекомендації та перераховувати вектор вподобань користувача. |
| SRS-FUN-07 | Система повинна надавати аналітику використання речей гардероба та формувати капсульний гардероб за заданим користувачем критерієм кількості речей. |
| SRS-FUN-08 | Система повинна кешувати результати сформованих рекомендацій засобами Redis з інвалідацією кешу при зміні складу гардероба. |
| SRS-FUN-09 | Система повинна видаляти персональні дані та фотографії користувача на його явний запит (право на видалення, GDPR). |

## 3. Non-Functional Requirements

| ID | Категорія | Вимога |
|---|---|---|
| SRS-NFR-PERF-01 | Продуктивність | Час відгуку (Latency) синхронних ендпоінтів API на перцентилі p95 не повинен перевищувати 200 мс при навантаженні 500 RPS. |
| SRS-NFR-PERF-02 | Продуктивність | Повний цикл асинхронної обробки одного CV-завдання не повинен перевищувати 5 секунд при паралельній обробці до 50 завдань на секунду. |
| SRS-NFR-SCALE-01 | Масштабованість | ML-інференс-сервіс повинен масштабуватися горизонтально до 10 Celery worker-інстансів без зміни коду. |
| SRS-NFR-SEC-01 | Безпека | Автентифікація повинна здійснюватися за OAuth 2.0/OIDC з JWT-токенами (RS256), термін дії access-токена не більше 15 хвилин. |
| SRS-NFR-SEC-02 | Безпека | Передача даних повинна здійснюватися виключно по TLS 1.3; дані в стані спокою повинні шифруватися. |
| SRS-NFR-SEC-03 | Безпека | API повинен обмежувати кількість запитів від одного клієнта (Rate Limiting) на рівні 100 запитів/хв на токен/IP засобами Reverse Proxy. |
| SRS-NFR-REL-01 | Надійність | При недоступності ML-інференс-сервісу споживач черги повинен застосовувати retry-політику з експоненційним backoff (не більше 3 спроб). |
| SRS-NFR-REL-02 | Надійність | При 3 послідовних невдалих зверненнях до ML-інференс-сервісу система повинна розмикати Circuit Breaker на 30 секунд, повертаючи останню кешовану рекомендацію замість помилки. |
| SRS-NFR-REL-03 | Надійність | Доступність (Availability) основного API повинна становити не менше 99.5%. |
| SRS-NFR-REL-04 | Надійність | Резервне копіювання PostgreSQL повинно виконуватися щоденно (daily snapshot) з точкою відновлення (RPO) не більше 24 годин. |

## 4. Verification Criteria

- SRS-FUN-01 верифікується інтеграційними тестами pytest, що перевіряють видачу JWT-токена та відмову в доступі за невалідним токеном.
- SRS-FUN-02a/02b верифікуються автоматизованими тестами Celery-завдань (pytest + Celery test workers) та перевіркою факту збереження файлу в Object Storage.
- SRS-FUN-03/04 верифікуються unit-тестами ML-пайплайну з фіксованим тестовим зображенням та перевіркою запису embedding у БД.
- SRS-FUN-05/06 верифікуються unit-тестами розрахунку косинусної схожості (pytest) та end-to-end тестом сценарію фідбек → перерахунок вектора.
- SRS-FUN-09 верифікується інтеграційним тестом видалення облікового запису з перевіркою відсутності записів у БД та Object Storage.
- SRS-NFR-PERF-01 верифікується навантажувальним тестуванням засобами k6 (сценарій Load Testing, стала 500 RPS, вимір p95).
- SRS-NFR-PERF-02 верифікується k6-сценарієм Spike Testing черги CV-завдань з вимірюванням end-to-end через Celery Flower/Prometheus.
- SRS-NFR-SCALE-01 верифікується навантажувальним тестом з горизонтальним масштабуванням Celery worker-інстансів у Docker Compose.
- SRS-NFR-SEC-01/02/03 верифікуються статичним аналізом коду SonarQube, сканером вразливостей Trivy та Postman-колекцією тестів авторизації й rate limiting.
- SRS-NFR-REL-01/02 верифікуються chaos-тестом (штучне відключення ML-сервісу) з перевіркою спрацювання retry-політики та стану Circuit Breaker у логах.
- SRS-NFR-REL-03/04 верифікуються моніторингом Prometheus/Grafana (аптайм) та перевіркою наявності snapshot-файлів резервного копіювання.

## 5. Glossary

- **Embedding** — векторне представлення зображення або профілю вподобань користувача у латентному просторі моделі.
- **JWT (JSON Web Token)** — компактний підписаний токен автентифікації, що передає claims користувача.
- **Latency (p95)** — час відгуку, нижче якого потрапляє 95% запитів.
- **RPS (Requests Per Second)** — кількість запитів, оброблюваних системою за секунду.
- **RPO (Recovery Point Objective)** — максимально допустимий обсяг втрачених даних у разі збою, виражений у часі.
- **Circuit Breaker** — патерн відмовостійкості, що тимчасово блокує виклики до сервісу, який демонструє стабільні збої.
- **Content-based filtering** — метод рекомендацій, що базується на схожості характеристик об'єктів, а не на поведінці інших користувачів.

## Додаток: Протокол аудиту ШІ-Аудитора вимог (ISO/IEC/IEEE 29148)

**Виявлені зауваження:**
1. Вимога SRS-FUN-02 (первинна версія) поєднувала дві системні дії — приймання фото та постановку завдання в чергу — в одному пункті. Виправлено: розділено на SRS-FUN-02a та SRS-FUN-02b.
2. Виявлено архітектурну прогалину (Gap Analysis): у початковій чернетці був відсутній компонент фізичного зберігання фотографій (Object Storage) — специфіковано лише запис embedding у БД, але не самого файлу зображення. Додано SRS-FUN-02a та окремий контейнер Object Storage (MinIO) у Розділі 2.
3. Виявлено відсутність вимоги Rate Limiting на рівні API — додано SRS-NFR-SEC-03.
4. Виявлено, що патерн Circuit Breaker, задекларований ще на етапі ЛР№1 як інженерне ускладнення проєкту, не потрапив до формального SRS — додано SRS-NFR-REL-02.
5. Виявлено відсутність вимоги на право видалення персональних даних (GDPR) — додано SRS-FUN-09.

**Відхилені рекомендації (з обґрунтуванням):**
- ШІ-аудитор рекомендував специфікувати багатовузлову (multi-region) реплікацію PostgreSQL для підвищення Availability понад 99.9%. Рекомендацію відхилено: система розгортається в межах одного локального/хмарного вузла в обсязі кваліфікаційної роботи одного студента; повна реплікація вимагає інфраструктури, не передбаченої обсягом проєкту. Залишено вимогу SRS-NFR-REL-04 (daily backup, RPO ≤ 24 год) як достатню для заявленого масштабу.
- ШІ-аудитор рекомендував додати окремий Identity Provider (наприклад, Keycloak) як самостійний контейнер. Рекомендацію частково відхилено: авторизаційна логіка реалізована в межах Backend API як окремий модуль/роутер (не є ancient/legacy tight coupling, а свідомий інженерний компроміс обсягу MVP), окремий IdP-сервіс визнано надлишковим для єдиного клієнтського застосунку в межах бакалаврської роботи.
