# ADR-001: Вибір сховища для векторних embeddings

**Статус:** Approved

## Context

Функціональні вимоги SRS-FUN-04 та SRS-FUN-05 вимагають зберігання векторних представлень (embeddings) речей гардероба та швидкого пошуку найближчих сусідів для формування рекомендацій. Нефункціональна вимога SRS-NFR-PERF-01 обмежує латентність синхронних запитів API на рівні p95 ≤ 200 мс при 500 RPS. Очікуваний масштаб даних для кваліфікаційної роботи одного студента — від кількох тисяч до десятків тисяч записів embeddings, без перспективи промислового мультитенантного навантаження в межах строку виконання роботи.

## Alternatives

1. **PostgreSQL + розширення pgvector** — зберігання embeddings як стовпця vector у тій самій реляційній БД, що вже використовується для користувачів і гардероба.
2. **Виділена векторна база даних (Qdrant, self-hosted)** — окремий сервіс, спеціалізований на наближеному пошуку найближчих сусідів (ANN).
3. **Керований хмарний векторний сервіс (Pinecone, SaaS)** — зовнішній API без необхідності самостійного адміністрування інфраструктури.

## Decision

Обрано **PostgreSQL з розширенням pgvector (індекс HNSW)**.

Обґрунтування: по-перше, зберігання embeddings в тій самій СУБД, що й реляційні дані користувача, виключає проблему розподіленої консистентності між двома джерелами даних (uncoordinated dual-write) та дозволяє виконувати фільтрацію за атрибутами (сезон, стиль) і векторний пошук в межах одного SQL-запиту без мережевого переходу між сервісами. По-друге, для заявленого обсягу даних (тисячі–десятки тисяч векторів) pgvector з індексом HNSW забезпечує латентність пошуку в межах одноцифрових мілісекунд, що залишає суттєвий запас у бюджеті SRS-NFR-PERF-01 (p95 ≤ 200 мс). По-третє, виділена векторна БД (Qdrant) додає окремий інфраструктурний компонент, окрему модель резервного копіювання та додаткову точку відмови без виправданої переваги на заявленому масштабі даних. По-четверте, керований хмарний сервіс (Pinecone) вносить мережеву латентність поза контролем системи (додатковий HTTP round-trip до зовнішнього API) та рекурентну грошову вартість (FinOps), не обґрунтовану бюджетом студентського проєкту, а також створює ризик Vendor Lock-in.

## Consequences

**Позитивні:**
- Єдине джерело правди (single source of truth) для реляційних і векторних даних; атомарні транзакції.
- Менша інфраструктурна складність: один додатковий компонент (розширення), а не окремий сервіс.
- Нижча вартість володіння (FinOps): без додаткового хмарного рахунку чи виділеного обчислювального вузла.
- Відсутність Vendor Lock-in: дані залишаються у стандартній реляційній СУБД.

**Негативні (чесно визнані компроміси):**
- pgvector з наближеним пошуком (HNSW) поступається спеціалізованим векторним базам даних за швидкістю пошуку на наборах даних порядку мільйонів і більше векторів — це технічний борг, прийнятий свідомо під заявлений масштаб проєкту.
- Індексація HNSW у pgvector вимагає ручного підбору параметрів (m, ef_construction) та має менш зрілу екосистему моніторингу порівняно з нативними інструментами Qdrant.
- У разі майбутнього зростання бази користувачів понад ~1 млн записів embeddings знадобиться окрема міграція на виділену векторну БД — у документі зафіксовано це як відомий шлях масштабування (scaling path), а не як приховану проблему.

## Додаток: Протокол аудиту ШІ-Архітектурного Судді (ADR Reviewer)

**Виявлені зауваження:**
1. У первинній чернетці альтернатива Pinecone була відхилена лише фразою «дорого» без конкретних метрик — ШІ-суддя зажадав перевести аргумент у площину інженерних метрик. Додано явне обґрунтування: мережева латентність зовнішнього API порушує бюджет SRS-NFR-PERF-01, а рекурентна вартість SaaS не виправдана обсягом проєкту (FinOps).
2. ШІ-суддя вказав, що початкова версія розділу Consequences не містила жодного негативного наслідку («рішення виглядало як вибір без компромісів») — це визнано недопустимим з інженерної точки зору. Додано секцію з трьома чесно визнаними негативними наслідками, включно з явним зазначенням межі масштабованості (~1 млн векторів) та шляху міграції.
3. ШІ-суддя рекомендував розглянути гібридний варіант (PostgreSQL для реляційних даних + Qdrant виключно для embeddings) як проміжний компроміс. Рекомендацію взято до відома як потенційний Фаза 2 проєкту, але не включено до поточного рішення ADR-001, оскільки це виходить за межі обсягу кваліфікаційної роботи; зафіксовано у негативних наслідках як «відомий шлях масштабування».
